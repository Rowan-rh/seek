## Context

当前内置链路的外部查询步骤已有结构化 evidence 门禁，但 `default` 链路从日志/trace 直接进入根因汇总，报告模板也只要求“直接原因、根本原因、因果链”。这能定位异常在哪一行暴露，却不能保证调查过“为何只有该对象失败”。链路定义存在人类编辑镜像和运行时资源副本，所有修改必须同步。

## Goals / Non-Goals

**Goals:**
- 把横向对照变成最终归因前的显式证据步骤，而不是报告写作建议。
- 用稳定枚举和分层字段区分数据触发、代码主因、共同作用及证据不足。
- 在没有可比样本时降低结论强度，避免代码位置替代业务根因。
- 让报告读者能复核样本为何可比、哪些字段不同、有哪些反证。

**Non-Goals:**
- 不自动生成 SQL 或自动选择业务表。
- 不自动判定业务数据是否合法；合法性仍来自 schema、业务约束、正常样本或复现。
- 不要求任何生产数据写操作；“修正后验证”可在预发、本地回放或由已有修复记录证明。
- 不改变旧会话或用户自定义链路的持久化格式。

## Decisions

### D1. 在默认链路新增独立证据步骤

在 `query-trace` 与 `analyze-root-cause` 之间增加 `compare-control-samples`。独立步骤比把要求塞进最终提示更可审计，也能利用现有 `evidenceRequired` 阻止未取证即推进。步骤输出异常样本、正常样本、可比性、差异、归因类型、置信度与反证。

备选方案是在 `analyze-root-cause` 中仅增加一段提示；该方案无法通过步骤状态识别对照是否真的执行，因此不采用。

### D2. 使用“首要归因 + 次生问题”的分层模型

根因类型使用稳定枚举：`DATA_SOURCE_PRIMARY`、`CODE_PRIMARY`、`DATA_CODE_INTERACTION`、`EXTERNAL_DEPENDENCY_PRIMARY`、`INSUFFICIENT_EVIDENCE`。报告另外保留 `direct_failure_point`、`primary_trigger`、`contributing_factor`，避免把代码抛错点、数据触发条件和容错缺陷挤进一个自由文本字段。

### D3. 正常样本按最小差异原则选择

优先级固定为同环境、同版本、同业务类型、时间邻近；比较维度至少覆盖输入/DB 数据、配置、部署版本、关键中间状态、执行路径和结果。弱可比样本必须披露差异，多个候选时说明选择或排除理由，降低挑选性偏差。

### D4. 无对照时允许流程完成，但禁止确定性归因

生产快照可能已过留存期或没有权限。此时步骤可用合法 `NO_DATA`/`TOOL_ERROR` evidence 完成，输出 `INSUFFICIENT_EVIDENCE`，而不是永久阻塞流程。若存在直接复现或数据修正前后验证，可作为等价对照。

### D5. 工单链路在现有深度排查步骤内扩展

`alert-ticket` 已有较多步骤和条件分支，不再新增步骤；在 `deep-investigate` 中增加对照输出，并让 `generate-report` 显式依赖这些字段。通用链路则新增独立步骤，以便普通故障排查形成清晰门禁。

## Risks / Trade-offs

- [查询成本和耗时增加] → 限制为优先 1–3 个高可比样本，先比较最可能区分根因的字段。
- [不同业务难以定义“正常”] → 要求记录可比性理由和不一致条件，不把弱对照当确定性证据。
- [已有 Agent 可能只填占位文本] → 通过 evidenceRequired、输出字段、模板测试和 Harness 场景共同约束。
- [根因枚举过于简化] → 保留自由文本的触发根因、次生因素和反证，枚举仅用于主归类。

## Migration Plan

1. 同步修改两份内置链路定义和两份报告模板。
2. 更新 Skill、SOP、证据规范、版本记录与测试。
3. 新启动会话使用新步骤；已有会话继续使用会话中已持久化的链路快照。
4. 如需回滚，恢复链路与模板文件即可，不涉及数据库迁移。
