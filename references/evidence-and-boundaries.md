# 证据与结论边界

本页只在排查需要日志、数据库、trace 或跨区域验证时加载。它定义“查到什么可以下什么结论”，不替代 `seek chain` 的步骤约束。

## 最低证据标准

每个重要结论都记录：

- 观测时间、环境、项目和查询窗口；
- 使用的命令、查询条件和返回上限；
- 原始证据中的关键字段（日志、trace、SQL 结果或外部任务 ID）；
- 结论、未验证假设和验证边界。

没有直接证据时使用“推测”“待验证”，不要写成已确认事实。

## SLS 查询

- `seek sls logs` 适合快速检索；需要精确字段、聚合或 SQL `limit` 时使用 `seek sls query`。
- 查询结果达到 `--max` 上限时，结果可能不完整。先缩小时间窗、增加 `--max` 或拆分查询，再下结论。
- 中文长句可能受分词影响。优先用 uuid、traceId、接口名、短业务词、状态词做互补查询。
- 至少用两个互补条件交叉验证关键结论，避免单个关键词命中造成误判。
- 不要使用 `not "cache"` 这类高频否定条件作为唯一依据，它可能同时过滤 `evict` 等关联日志。
- 复杂 SQL（单引号、中文、`"__tag__:__hostname__"` 双引号列名混排）不要直接拼在 shell 里，写入文件后用 `seek sls query --query-file <file>`（或 `-` 读 stdin）传入；回溯历史时段用 `--time "YYYY-MM-DD HH:MM:SS,YYYY-MM-DD HH:MM:SS"`，不要手算 unix 时间戳。

### 关键词搜索静默返 0：无索引或分词不匹配

裸关键词搜索**静默返回 0 条**有两种独立成因，都极易误判"任务没执行/没有日志"：

1. **无全文索引**：logstore 只建了字段索引（如 `level`）。用已知必存在的词试探（如 `level: INFO`）：索引字段查询有结果、裸关键词却全 0，即 message 无全文索引；
2. **分词不匹配**（索引形态完全正常也会发生）：全文索引存在，但分词器对中文长词（如"指标同步"）、驼峰类名（如 `MetricSyncTask`）不切分出对应 token，关键词查询照样 0 条。实测案例：`"指标同步"` 关键词查询 0 条，而 SQL `where message like '%指标同步%'` 同窗口命中 56 条。

识别与处置：

1. `seek sls query` 关键词查询返空时会自动探测 GetIndex，并把结论写入返回的 `warnings`/`indexCheck`，必须先看再下结论；
2. 即使 `indexCheck` 显示"有全文索引"，下"未执行/无数据"结论前也必须用 `* | select ... where message like '%关键词%'` SQL 全扫描交叉验证（like 不走分词）；
3. 或改用日志中实际出现的短词/业务词、索引字段（`level: ERROR`）查询。

### 文档 logstore ≠ 活 logstore

配置/文档记载的 logstore 可能已停写（如应用 SLS appender 被注释下线），结构存在但长期 0 条日志。回溯排查前先做活性验证：

- `seek doctor --liveness-window 30d`：窗口内 0 条标记 `stale`；
- 命中 stale 时切换到同应用其它候选 logstore（如 `*_aso` 系列）重新验证，并在报告中记录"文档记载的 logstore 已失效"这一事实。


## 跨 region 边界

“当前 logstore 查不到”不等于“应用没有接入 SLS”或“系统没有产生日志”。

查不到应用日志时必须：

1. `seek sls config <project>` 核对目标环境的全部 logstore；
2. 使用 `seek doctor` 实测配置指向的 project/logstore 是否存在；
3. 至少检查杭州、上海等主要 region，或明确记录无法访问的 region；
4. 仍无结果时，将结论写成“已验证的 region 和时间窗内未发现”，并列出未覆盖范围。

配置文件只能说明声明过一个目标，不能证明目标仍真实存在。

## Trace 缺失时的替代证据

没有 traceId、trace 未接入或调用链文档缺失时，不要伪造 trace 结论。可使用：

- 本地源码搜索调用点、注解、MyBatis SQL 和事务/异步边界；
- SLS 中同一 uuid、业务键或请求标识的时间线；
- 上下游服务的请求/响应日志。

报告中明确标记这是替代证据，并区分“观测到的调用”与“根据代码推断的调用关系”。

## DB 查询边界

- 只执行只读 `SELECT`、`WITH`、`EXPLAIN` 查询，并控制返回量。
- DMS 无权限、数据库未注册或连接失败时，记录失败原因，不把“无法查询”写成“无数据”。
- 可用 `SELECT * FROM <table> LIMIT 1` 探测列名，但不要借此推断全表状态。
- SQL 结果应记录数据库标识、表、过滤条件和时间范围，避免脱离上下文引用孤立结果。
- 配置指向的库也可能已停写（与停写 logstore 同理）：已证实本地直连日常库 `stability-locate-daily-locatenew`（`stability_locate_new`）最后写入停在 2025 年初，非当前日常部署真实库。判定方法 `SELECT MAX(gmt_created)`；"该库查无记录"不能证明数据不存在，日常数据证据以 SLS 为权威。

## 根因归因与正常样本对照

异常堆栈、代码行和防御性判断缺失只能证明**直接报错点**或**容错缺口**。要把问题归因为代码、数据、配置或外部依赖，必须回答“同样代码下，正常实例和异常实例从哪里开始不同”。

### 样本选择优先级

1. 同环境、同部署 commit、同业务类型、时间邻近的成功实例；
2. 同环境同版本但时间较远的成功实例；
3. 跨环境或跨版本样本仅作弱证据，必须声明差异；
4. 没有自然正常样本时，可使用本地/预发直接复现或数据修正前后结果作为等价对照。

每个样本记录业务主键、时间、环境、版本、查询来源和选择理由。不得只挑支持既有猜测的样本；存在其他候选时记录排除理由。

### 最低比较维度

- 输入与 DB 源数据：空值、非法枚举、关联缺失、顺序、重复、状态组合；
- 配置与版本：环境配置、开关、部署 commit、依赖版本；
- 中间状态：集合规模、首个分叉步骤、状态机迁移、上游返回；
- 执行路径与结果：是否进入同一分支、是否成功、最终错误是否只是二次异常；
- 反证：同样异常数据是否也有成功案例，正常数据是否也会失败。

### 分层结论

- `direct_failure_point`：最终抛错或失败的位置；
- `primary_trigger`：最早导致正常与异常样本分叉的条件；
- `contributing_factor`：未正确校验、降级或报错而放大影响的次生问题；
- `attribution_type`：`DATA_SOURCE_PRIMARY` / `CODE_PRIMARY` / `DATA_CODE_INTERACTION` / `EXTERNAL_DEPENDENCY_PRIMARY` / `INSUFFICIENT_EVIDENCE`；
- `attribution_confidence`：高/中/低，并说明由哪些证据和反证决定。

若只有代码堆栈，没有异常输入快照、正常对照、直接复现或修正前后验证，结论必须是 `INSUFFICIENT_EVIDENCE`。用户提供的根因说明属于待验证线索，不能替代独立证据。

## 更正规则

如果发现查询条件过窄、结果被截断或前序结论错误：

```text
seek chain amend <session> --step <N> \
  --summary "原查询/原结论；修正原因；新查询/新证据" \
  --outputs '{...}'
```

更正追加记录，不覆盖原始输出。报告中保留更正原因、受影响结论和新的验证边界。
